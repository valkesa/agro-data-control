# N7.1 — Persistencia real de configuración + aplicación de BoardPreset a Device

Implementado el 19/09/2026. Primera etapa de la serie N7 que conecta el subsistema de templates/capacidades/BoardPreset (construido 100% en memoria desde N1 a N6.5.2) con Firestore real, sin tocar el TABLERO productivo.

- **Auditoría previa (§1):** se confirmó que `tenants/{tenantId}/devices/{deviceId}` (hermano de `sites`, no anidado) es el path vigente; `tenants/{t}/sites/{s}/plcs/{p}` es legacy y no se usa para nada nuevo. Las bibliotecas/perfiles/BoardPreset de N1-N6.5.2 no tenían ninguna colección Firestore propia todavía — se crearon 6 colecciones globales nuevas (`layoutTemplates`, `cellLayoutPresets`, `capabilityMetrics`, `capabilityIndicators`, `capabilityProfiles`, `boardPresets`) con IDs elegidos por el caller (slugs), nunca auto-ID, siguiendo el mismo patrón que `deviceTemplates`.
- **Separación config global vs. per-Device (§3):** lo global (BoardPreset, bibliotecas, perfiles) vive en colecciones top-level sin tenant. Lo específico de un Device vive en un documento singleton nuevo `tenants/{tenantId}/devices/{deviceId}/settings/boardConfig` — deliberadamente una subcolección nueva bajo el Device ya existente, para no tocar el schema/reglas del propio documento `devices/{deviceId}` (cumple §18: cero cambios en el TABLERO productivo).
- **Repositorios, nunca Firestore directo desde widgets (§4):** un repositorio por entidad (`LayoutTemplateRepository`, `CellLayoutPresetRepository`, `CapabilityMetricRepository`, `CapabilityIndicatorRepository`, `CapabilityProfileRepository`, `BoardPresetRepository`, `DeviceBoardConfigRepository`), todos con `FirebaseFirestore?` inyectable y lecturas one-shot (`fetchAll`/`fetchOne`, nunca `.snapshots()` — cumple §5, sin streams/polling nuevos).
- **Versionado (§6):** `schemaVersion`/`enabled`/timestamps en las bibliotecas de capacidades vía `CapabilityMetricRecord`/`CapabilityIndicatorRecord`; `presetVersion`/`layoutVersion` como contador optimista en `BoardPreset`/`DeviceBoardLayout`. Los timestamps cruzan el límite toMap/fromMap siempre como `DateTime`/ISO-8601 UTC — nunca un `Timestamp` crudo llega a un modelo puro (adaptador compartido `firestore_timestamp_adapter.dart`).
- **Aplicar preset = copia por valor, nunca referencia viva (§8/§9):** `applyBoardPresetToDevice()` (Firestore-free, testeable puro) valida perfil/preset, resuelve el catálogo y arma un `BoardContentLayout` nuevo copiando cada item por valor; `DeviceBoardConfigRepository.applyPreset()` persiste ese resultado dentro de una transacción versionada. Solo sobrevive trazabilidad histórica (`sourceBoardPresetId`/`sourceBoardPresetVersion`) — nunca se vuelve a resolver en vivo contra el preset. Verificado en Chrome real: aplicar el mismo preset a dos Devices, editar uno, y el otro queda intacto; editar o **borrar** el preset de origen después nunca rompe un Device que ya lo aplicó (§10) — reproducido borrando `boardPresets/preset_demo_sala_a` con el Device ya configurado y confirmando que su `DeviceBoardLayout` sigue funcionando igual.
- **`BoardEditorMode.device` implementado (§13):** el enum ya existía desde N6.2 pero nunca se había cableado. `BoardEditorController.forDevice()` + `BoardEditorPage(deviceContext: ...)` reutilizan el mismo editor de siempre — nunca se creó un editor nuevo. Header propio ("CONFIGURACIÓN DE BOARD — DEVICE REAL"), sin selector de perfil-de-referencia libre (el perfil es el asignado al Device).
- **Dirty/save explícito, sin auto-save (§14):** `BoardSaveStatus {idle, saving, saved, error}`; el botón "Guardar" solo se habilita con cambios pendientes; el texto de estado distingue "Sin cambios · vN" / "Cambios sin guardar" / "Guardando…" / "Guardado · vN" / "Error al guardar: …".
- **Concurrencia optimista real (§15):** todo write pasa `expectedVersion`; un mismatch lanza `FirestoreVersionConflict`, nunca sobrescribe. **Bug real encontrado y corregido en esta etapa:** en Flutter Web, lanzar esa excepción *dentro* del callback de `runTransaction` le hace perder su tipo Dart al cruzar la Promise de JS interop (queda como un `"Dart exception thrown from converted Future"` genérico) — el catch específico de la UI nunca la reconocía y el diálogo `configuration_conflict` no aparecía (aunque el dato *nunca* se sobrescribía: la protección real ya funcionaba, solo fallaba el mensaje). Se corrigió devolviendo un sentinel desde la transacción y lanzando la excepción tipada *después*, en Dart puro — verificado provocando un conflicto real contra el emulador y confirmando el diálogo "configuration_conflict" en Chrome.
- **Reglas Firestore (§16):** 6 bloques nuevos para las colecciones globales (solo owner escribe) más un bloque para `devices/{deviceId}/settings/boardConfig` restringido al tenant dueño del Device. Verificado con un test de 11 escenarios contra el emulador real (owner/tenant_admin/otro tenant/no autenticado).
- **Seed idempotente, nunca auto-run (§17):** `tool/seed_n7_1_global_config.dart`, con `--dry-run`/`--overwrite`. No pudo reusar los stores `ChangeNotifier` existentes (`board_preset_catalog.dart` etc.) porque importan transitivamente `dart:ui` vía `flutter/foundation.dart`, inutilizable bajo `dart run` puro — se reconstruyó la lógica de construcción de datos de referencia en un builder propio del script, sourceado desde los archivos genuinamente libres de Flutter.
- **Nada de producción tocado (§18/§24):** cero cambios en TABLERO productivo, cero migración automática de Devices existentes, cero streams/polling nuevos, cero PLC runtime binding — `flutter build web` de `lib/main.dart` compila igual que antes de esta etapa.

**Otros hallazgos de la revisión propia** (no solo "los tests pasan"): 3 tests de reglas Firestore preexistentes (`test/tenant_management_page_test.dart`, `test/agro_structural_schema_test.dart`) extraen texto de `firestore.rules` con `String.indexOf`/`substring` en vez de balanceo real de llaves — son frágiles ante *cualquier* texto nuevo (código o comentario) insertado antes de sus marcadores, o ante un nuevo bloque cuyo path sea prefijo textual de un ancla existente. Se reprodujeron 3 fallos espurios reales durante el desarrollo (documentados en el informe) y se resolvió moviendo el bloque de reglas nuevo al final absoluto del archivo — la fragilidad de esos tests en sí queda como deuda técnica no resuelta por esta etapa. También se detectó (y no se investigó a fondo, por no ser bloqueante) que `flutter build web` en modo release produce una pantalla en blanco para estas páginas nuevas mientras que `--profile`/debug renderizan correctamente — se usó `--profile` para el recorrido Chrome de esta etapa; ver el informe HTML para el detalle.

Validación final: suite Flutter completa aprobada (1070 tests, 1 skip preexistente y ajeno), test de reglas del emulador (11/11), `dart format`/`dart analyze` sin cambios ni errores nuevos, `flutter build web` de `lib/main.dart` correcto. Recorrido real en Chrome headless vía CDP (perfil `--profile`, no release) contra Firestore+Auth emulators locales, con las 8 capturas obligatorias del prompt, incluyendo aplicar preset, editar en `BoardEditorMode.device`, estado dirty, persistencia tras recarga, independencia entre dos Devices, borrado del preset sin romper Devices, y el diálogo real de `configuration_conflict`.
